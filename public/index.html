Reverse infrastructure-as-code

Capture what you run, deploy what you captured.

TruthForm reads your live systems through each platform's own APIs and writes a normalised snapshot you can review, diff and redeploy. The running system is the source of truth, so there is no state file to manage. And because a snapshot is the system written down, it can be rewritten: an Azure snapshot translates, offline, into AWS or Google Cloud snapshots that restore the same way.

The other way round

Infrastructure-as-code

Write the code first, apply it, and keep a state file in step with reality. Anything changed by hand, or created by a tool nobody wrote code for, drifts out of view.

TruthForm

Run things however you already do. TruthForm reads what is actually there and writes it down as a snapshot you can restore, diff and review. One binary that runs inside your own environment with your own credentials, with no Terraform or Pulumi dependency.

How it works

  1. 1

    Capture

    Ask the platform which types exist, from its own published schemas, and read every resource. Custom and newly added types need no TruthForm code first.

  2. 2

    Snapshot

    Strip what the platform generated, turn IDs into references, and write one YAML file per resource, plus a report of everything left out and why.

  3. 3

    Restore or diff

    Recreate what is missing, in dependency order, into the same place or another one. Or compare the snapshot with what is live and see exactly what changed.

Nice to use

Quick to set up, plain about what it did, and safe to try on the systems that matter.

  • One binary, nothing beside it

    No server to run, no account to open, no state file to keep and nothing installed in the cluster. Unpack it on Linux, macOS or Windows and point it at what you already run, with the credentials you already have.

  • Access, written for you

    truthform permissions writes the exact grant a capture needs, in the platform's own tool, with the commands to deploy, verify and remove it. truthform check then runs a trial capture as that identity and names any type it still cannot read.

  • It tells you what it did not do

    Every snapshot opens with REPORT.md, and the first thing in it is what is incomplete. A type it was refused is reported as denied, never as empty, and a run that missed anything ends with exit code 3, so a partial result never passes for a whole one.

  • Infrastructure you can review

    One readable YAML file per object, written the same way every time, so git diff and a pull request work on a whole estate. truthform diff answers in a line, and exits 2 when something changed.

  • Look before it writes

    --dry-run checks a restore into AWS, Google Cloud, GitHub or Cloudflare against the target first. On Kubernetes, plan rebuild says what a restore needs. A restore that would quietly do the wrong thing is refused before anything is written.

  • Try it on a laptop

    A local kind cluster is all it takes: capture it, break something, see the diff, restore it and see the diff come back clean. No cloud account, and nothing to pay for.

  • No secret written down

    A snapshot holds a Secret's key names, never its values, so it can be committed and shared. A Kubernetes restore reads the values live, from the source cluster or from where they are kept, such as 1Password or Key Vault.

  • At home in scripts and agents

    Add --json to capture, diff, restore, compare, check, permissions, plan or translate for one JSON document on stdout, with the exit code unchanged. truthform mcp gives an AI agent the read-only commands, and no way to restore.

Azure to AWS or Google Cloud, offline

truthform translate reads an Azure snapshot and a short map you write, and writes a snapshot for the other cloud. It makes no request, so nothing is touched while you read the result, and plan, restore and diff take what it writes as they take any snapshot. It does not guess: every Azure object ends in a stated outcome, and the target is never more open than the source.

  • What it translates

    Service Bus, virtual networks and their routing (route tables, NAT, peerings), network and application security groups, flow logs, private endpoints, DNS zones, blob containers, Key Vault secrets, container registries, AKS clusters, the configuration of PostgreSQL and Azure SQL servers, and workload identity. Every other type is reported as not looked at.

  • Every object accounted for

    Each Azure object is mapped, mapped with losses, refused or not looked at, and translation.yaml says which and why. The run fails when anything is refused, not looked at or less protected than the source, so a partial translation never reads as a finished one.

  • Never more open than the source

    A translation may let through less than Azure did, never more. Azure's network security groups decide by priority, the first match winning; AWS security groups only allow. Each allow is written with every deny before it taken out, and what cannot be written exactly is narrowed or dropped, and named.

  • Evidence for an audit

    Every network rule, Azure's defaults included, gets a row for each place it is written: exact, stricter, not carried or does not apply, with the target rules that enforce it. The claim is tested by putting the same packets to Azure's rules and to each target's rules, as that cloud evaluates them.

  • Identity, narrowed to the object

    A pod that reached a queue, a blob, a secret or an image through its managed identity reaches the translated one, and nothing else: an IAM role for EKS Pod Identity, or a service account on GKE. A grant wider than one object is narrowed to the objects by name. Control-plane roles, custom roles and grants to people are refused.

  • Your Git repository too

    Workloads applied from Git still name Azure things. With --kube and --gitops, translate lists every image, KEDA trigger and address there that must change, by file and line, with what it becomes on the target. It rewrites no manifest: the repository is yours.

  • A dry run against the target

    restore --dry-run on AWS and Google Cloud reads the target and lists each write. It also finds what would refuse one: a bucket name someone else holds, a role or service account that does not exist, an API not enabled. What it could not check is printed as NOT CHECKED.

  • Skills for what is left to people

    Data is never copied and machines are not translated. Six skills, built into the binary and served over MCP, let an agent help a person with the rest: moving data, granting refused access, rebuilding machines, a database's TLS floor, flow log parsers, and an estimate of the cost on the target. Each checks its own work and leaves every write to the person.

Where it stands

Translations are restored into simulated AWS and Google Cloud APIs, and every object is built through the CloudFormation registry or checked against Google's Discovery documents. The dry run has been run read-only against a test AWS account and a test Google Cloud project, with translations of about 1,400 and 1,100 objects: it wrote nothing, caught the two cluster roles the test map made up as missing on AWS, found three APIs not enabled on Google Cloud, and found every bucket name free. No translation has yet been restored into a real AWS or Google Cloud account. Azure is the only source so far.

What works today

In beta. Everything below is built, and the proof for each platform is listed underneath, including where it is still simulated.

  • Six platforms, read from their own schemas

    No hand-written list of fields per type: Kubernetes discovery, AWS Cloud Control with the CloudFormation registry schemas, Azure Resource Manager, Google Cloud Asset Inventory with Discovery documents, and GitHub and Cloudflare through their OpenAPI descriptions.

  • Read-only by construction

    Capture and diff run behind a guard on the HTTP transport that refuses any write before it leaves the machine. A capture-only edition refuses to restore at all.

  • Redeployable, not a dump

    What the platform set itself, such as generated IDs, status and timestamps, is kept apart from what you configured and never sent back. References such as a subnet's VPC, a role's ARN or a principal ID are remapped to whatever the target creates.

  • Deterministic output

    An unchanged system captures to byte-identical files, so CI can regenerate snapshots and a diff shows only real change.

  • Honest coverage

    Every snapshot has a REPORT.md that leads with what is incomplete. A refused read is a failure, never an empty result, and every skip has a reason.

  • Secrets stay out

    Secret values, keys the platform never returns, and webhook URLs that are themselves credentials are named, not written. So is a credential left as plain configuration in Kubernetes, in an env list or a ConfigMap, and the report tells you to move it into a Secret. Values are supplied at restore time.

  • Restore that fails loudly

    Dependency order, in parallel on AWS, Azure and Google Cloud. On the clouds and SaaS it creates only what is missing; --update brings drift back in line and never replaces a resource. Anything not applied is reported.

  • A plan for what a snapshot cannot hold

    A cluster rebuilt from a snapshot also needs what is not in it. truthform plan rebuild lists that in the order to act on it: what to install first, the APIs that must be served, the Secrets a person keeps a copy of, the ones a store supplies, and the hosts to point at the new cluster. It reads only the snapshot.

  • Secrets read from where they live

    A secret sources file says where each Secret's copy is: 1Password, Azure Key Vault, an environment variable, a file, or a command. It holds references, never values, so it can sit in a repository. plan secrets --check --resolve proves every source answers before a rebuild needs it, and a read that gives nothing is refused, so a lapsed sign-in never restores an empty password.

  • Restore a part, held

    A scope file picks namespaces, Helm releases and labels, and hold restores what it picks with nothing running. A restore is refused, with nothing written, when a GitOps source brought beside a hold would start what is held (unless it is held too, or accepted by name), or when an admission webhook that fails closed would call a Service that will not answer.

  • Into another environment

    On Kubernetes, --leave-out keeps the new cluster from syncing the source's GitOps path, and --rename points every secret store reference at the new environment's stores. A reference no rename reaches refuses the restore, so a copy never quietly reads production's vault.

  • Diff for pipelines

    Missing, extra and changed resources with the fields that changed. Exit codes tell outcomes apart, and --json gives one document a pipeline can read.

  • A whole environment at once

    One config lists clusters, AWS regions, Azure subscriptions, GCP projects, GitHub organisations and Cloudflare accounts. They are captured in parallel, and one unreachable target does not stop the rest.

  • The estate as a graph

    On Azure, truthform graph writes a snapshot as resources and their relationships, in deterministic JSON, for an asset inventory or a security graph. It reads only the snapshot: no login, no requests.

  • Built for agents too

    truthform mcp tells an AI agent every field of a resource type, captures and diffs, says what access to grant and what a grant can read, and serves the translation skills. No tool can change your systems, and there is deliberately no restore tool.

Proven by restore drills

A drill seeds a system, captures it twice and requires identical digests, deletes what it seeded (on Kubernetes, starts a fresh cluster instead), restores it from the snapshot, and requires zero differences. Every run below was against real systems unless it says otherwise.

  • KubernetesA 13-object application, CRD and custom resource included, restored from one kind cluster into a fresh one with the secret values intact. The same drill runs against real API servers on every pull request that changes code.
  • AWS21 resources across 17 types in a sandbox account, an IAM role, a managed policy and a Lambda function among them, restored under new IDs with their references intact. Into another region too: 16 of 16 across 13 types.
  • Azure7 resources in a sandbox subscription: resource group, network security group and its rule, virtual network, managed identity, a role assignment and a lock. The restored role assignment names the restored identity.
  • Google CloudA service account and a notification channel whose ID the server assigns, in a sandbox project. Compute is proven against a simulated API only.
  • DriftOn AWS, Azure and Google Cloud the drills then change resources by hand: a plain restore reports the drift, restore --update brings it back, and the diff is empty again.
  • GitHubReal read-only captures of an organisation. Restore and update are proven against a simulated API built from GitHub's own OpenAPI description.
  • CloudflareReal read-only captures of an account's zones and DNS records, signed in through the browser. Restore is proven against a simulated API built from Cloudflare's own OpenAPI description.
  • 4m33s → 135sThe AWS drill's restore of 17 resources, one at a time and then in parallel along the dependency graph.
  • 1,498 types, 4m52sA full read-only capture of one AWS region. Two consecutive runs were byte-identical.
  • 29sFour sandboxes (Kubernetes, AWS, Azure, Google Cloud) captured from one config, complete.

Measured on the sandbox drills in October 2026. Parallel restore gains least where resources depend on each other: the Azure drill's single long chain went from 23s to 19s, Google Cloud's two independent resources from 10s to 4s.

Roadmap

Planned, not built.

  • Planned

    More SaaS providers

    Okta, Datadog and others, on the same OpenAPI-driven engine as GitHub and Cloudflare.

  • Planned

    A translation restored for real

    A translated Azure environment restored into a real AWS account and a real Google Cloud project, with an empty diff.

  • Planned

    More of Azure translated

    The types and settings reported as not looked at today, such as a storage account's lifecycle rules and replication, each decided one by one.

  • Planned

    Secrets on AWS

    Secrets Manager values read live from a source account, as Kubernetes restores already read Secrets from a source cluster.

  • Planned

    Drift that opens pull requests

    Agents watch for drift and open a pull request; deterministic snapshots mean it shows only real change.

  • Planned

    Snapshots as MCP resources

    So an agent can read a snapshot without a tool call.

  • Planned

    Scheduled restore drills

    Restore into a sandbox on a schedule, per platform, and require an empty diff.

  • Planned

    Wider real-world proof

    Cross-account restores on AWS, Compute on real Google Cloud, a Cloudflare restore into a real zone, and principals across Azure tenants.

Download

TruthForm is in beta. It is one binary, under the Apache License 2.0, that you run inside your own environment with your own credentials. There is no TruthForm service behind it, so your configuration stays with you.

The current release is v0.1.0-beta.26: Linux, macOS and Windows, each for amd64 and arm64, in a full and a capture-only edition, with a SHA256SUMS file and signed build provenance. Getting started shows how to check a download and how to build from source. The source and every release are on GitHub.
