Rebuild a cluster

A snapshot recreates what it holds. A Kubernetes cluster rebuilt from one also needs what it does not hold: the tools that install the rest, the Secrets' values, the names that point at it. These commands say what that is, read it from where it lives, and refuse a restore that would quietly do the wrong thing.

The rebuild plan

truthform plan rebuild --from snap/cluster                 # Markdown, to stdout
truthform plan rebuild --from snap/cluster --out PLAN.md
truthform plan rebuild --from snap/cluster --json | jq '.plan.secretsByHand[].name'

It reads the snapshot and nothing else: no login, no request, and the capture-only edition has it. The same snapshot gives the same plan, so it can be kept beside the snapshot and compared like one. In the order to act on it:

  1. Install first: what the capture left to a GitOps source (a Flux HelmRelease or Kustomization, an Argo CD application, a Crossplane composite), with how many objects each makes.
  2. APIs to have served: types the snapshot has objects of and no CustomResourceDefinition for. The restore refuses those objects until something serves the type.
  3. Secrets to supply by hand: the ones no store in the snapshot supplies, with their keys and what names them. What the cluster makes again by itself, such as cert-manager's certificates, is named apart. Secrets kept encrypted are named with the key that opens them, the one thing only a copy outside the cluster brings back.
  4. Secrets a store supplies: the items read by the 1Password operator, External Secrets, the Vault Secrets Operator, the Secrets Store CSI driver and akv2k8s.
  5. Restore.
  6. Names to point at the rebuilt cluster: the hosts in Ingress rules, Gateway routes and Traefik matches.

A snapshot whose capture could not read everything gives a plan that says so first and lists what was not read: a step that lists nothing is then no proof there is nothing.

Where the secrets are read from

A secret sources file says where each Secret's copy is, so a rebuild reads the values itself. It holds references and never a value, so it can be kept in a repository beside the pipeline that uses it.

# a file to fill in, then: does every Secret have a source, and does each answer?
truthform plan secrets --from snap/cluster --out secrets.yaml
truthform plan secrets --from snap/cluster --check secrets.yaml
truthform plan secrets --from snap/cluster --check secrets.yaml --resolve
truthform restore --context new --from snap/cluster --secrets-from secrets.yaml
secrets:
  - secret: flux-system/flux-system
    from:
      username: env:GIT_USER
      password: op://Break Glass/flux git/password
  - secret: tools/licence
    leave: the vendor's operator makes it when it starts
ReferenceRead from
op://<vault>/<item>/<field>1Password, with the op CLI
azurekv://<vault>/<secret>Azure Key Vault, with the az CLI
env:<NAME>An environment variable
file:<path>A file's whole content, byte for byte
exec:<command>What a command prints; only with --allow-exec
empty:The empty value, for a key meant to hold nothing

A read that gives nothing is refused, so a sign-in that lapsed does not restore an empty password. A key that is meant to be empty says so with empty:.

A part of the snapshot

A drill wants the platform, the core of an application and a few of its workloads, not everything. A scope file says which, in terms the cluster already has:

truthform plan scope --from snap/cluster --out scope.yaml     # brings everything; never written over one
truthform plan scope --from snap/cluster --check scope.yaml   # what it brings, and what it leaves out
truthform restore --context test --from snap/cluster --scope scope.yaml
truthform diff    --context test --from snap/cluster --scope scope.yaml
narrow:
  - namespaces: ["team-*"]          # names, or patterns as a shell has them
    releases: [a-search, b-search]  # Helm releases, in any of those namespaces
    objects: [ConfigMap/shared]     # what no release made, as Kind/name
  - namespaces: [batch]
    labels: {tier: drill}
    hold: true                      # restored, not running

A scope narrows the namespaces it names and leaves the rest of the snapshot as it is, so a namespace added later that a pattern fits is left out until someone chooses from it. A release comes whole, wherever what it made is. hold: true brings what an entry chooses with nothing running: workloads at zero, sources suspended.

A restore is refused, with nothing written, when:

  • A GitOps source brought beside a hold would start what is held. A scope cannot stop a source that is brought from making what it makes. Hold the source too, leave it out, or accept it by name under sourcesRunning.
  • An admission webhook that fails closed would call a Service that will not answer. Webhooks are applied last, so the first restore would go through; from then on the API server refuses every write the webhook is asked about. This is asked of every Kubernetes restore, with a scope or without one.

Into another environment

A snapshot restored beside its source, for a drill or to build one environment as another, needs two things changed and nothing else.

truthform restore --context test --from snap/cluster \
  --leave-out leave.yaml --rename stores.yaml --secrets-from secrets.yaml
truthform diff    --context test --from snap/cluster --leave-out leave.yaml --rename stores.yaml
  • --leave-out lists objects the restore does not write and the diff does not expect, as Kind/namespace/name with * for any part. The first to leave out is where GitOps starts: restored as it is, the new cluster would sync the source's path.
  • --rename says where Secrets are read from instead: the start of a store reference, and what replaces it. Only fields that name a store or an item in it change, across 1Password, External Secrets, the Vault Secrets Operator, the Secrets Store CSI driver and akv2k8s. A restore is refused while any store reference is left unnamed or out of reach, because what reads through it would use the source's store: the copy would quietly read production's secrets.

What it cannot see

  • Who uses a Secret, when the user is something step 1 installs, or an object with no namespace that names the Secret without one.
  • Which namespaces a ClusterExternalSecret reaches; its Secrets are listed as */name.
  • A secret store of a kind the plan does not know: its Secrets are listed as by hand.
  • Hosts matched by pattern, such as Traefik's HostRegexp.
  • Data: databases, volumes and queues are outside a snapshot.
