Permissions

A capture only reads. Grant it a read-only role, and run it with the capture-only edition, which cannot send a write whatever it is given. A restore creates and changes resources, so it needs write access: grant that separately, for the restore only.

Build the grant, then check it

You do not have to build these by hand. truthform permissions writes the grant as a template for the platform's own tool (a CloudFormation stack, an Azure deployment stack, Terraform, a Kubernetes manifest; for GitHub and Cloudflare, the exact token settings) and prints every command to check what is there first, deploy it, verify it and remove it again, with your values filled in. It grants nothing itself.

truthform permissions --platform aws --account 111122223333 \
    --principal arn:aws:iam::111122223333:role/ops --source-profile ops

Then check what the grant can actually read, type by type, with a capture that is written nowhere. A type refused for want of permission is reported as denied, never as empty, and the check exits 3.

truthform check --platform aws --region us-east-1 --profile truthform-reader

Each grant below says whether it has been Verified, meaning TruthForm ran with exactly that access, or is Expected, meaning it follows from the platform's documentation and the calls TruthForm makes but has not yet been run with exactly that access.

AWS

TruthForm reads and writes through Cloud Control, which calls each service on TruthForm's behalf with the caller's own permissions. A role therefore needs Cloud Control's actions and the read (or write) actions of every service whose types are captured.

UseGrantStatus
Capture, diff The managed policy ReadOnlyAccess, plus TruthForm's read add-on, which truthform permissions puts in the role. ReadOnlyAccess covers Cloud Control's reads, sts:GetCallerIdentity, ec2:DescribeAvailabilityZones and most services' Describe*, Get* and List*, but not every newer service's. The add-on is the reads the CloudFormation registry's handlers name that ReadOnlyAccess lacks: 527 actions in three customer managed policies. A schema naming an action is not enough to grant it, because some reads return secrets that ReadOnlyAccess leaves out on purpose (ivs:GetStreamKey, glue:GetConnection), so it keeps only reads of configuration: no secret values, no data, no writes. It is regenerated weekly from AWS's public sources, with no AWS credentials, and each change is reviewed before it ships. ReadOnlyAccess itself also reads data (S3 objects, DynamoDB items). Verified
On 2026-10-24 the role truthform permissions builds captured a sandbox region with the same 97 resources as an identity holding ReadOnlyAccess and PowerUserAccess, and no sampled write was allowed. It was refused 2 of 1,161 types, both on purpose: a data-plane type and one holding credentials. The sandbox holds little, so that count is a floor: about 37 types need a refused action just to be listed (AWS::Glue::Connection among them), and an account using them sees them reported as refused, not empty. ReadOnlyAccess alone was refused 87 types. A trust from another account is not yet verified.
Restore cloudformation:CreateResource, cloudformation:UpdateResource, cloudformation:GetResourceRequestStatus, plus each service's create and update actions. PowerUserAccess covers every service except IAM. Verified
With PowerUserAccess, for the 15 non-IAM types the restore drill uses. Creating a Lambda function also needs iam:PassRole on its role.
Restore IAM types Add IAM write (iam:CreateRole, iam:PutRolePolicy, iam:AttachRolePolicy, iam:CreatePolicy, iam:TagRole, …) and iam:PassRole for anything that takes a role, scoped to the names being restored. Verified
On 2026-10-24, for a role and a customer managed policy attached to it, with IAM write limited to roles and policies named truthform-drill*: deleted and restored with no diff, and brought back from drift by --update.

ViewOnlyAccess is not enough. It omits many of the Get* reads Cloud Control's handlers make, and those types are reported as failed in coverage.yaml.

Azure

UseGrantStatus
Capture, diff The built-in Reader role at the subscription. It reads every resource, and the extension resources TruthForm captures: role assignments and custom role definitions, locks, policy assignments and diagnostic settings. Verified
On 2026-10-23, a service principal holding only Reader captured a sandbox subscription to the same digest as its owner.
Restore Contributor, plus User Access Administrator for role assignments and locks (Microsoft.Authorization/*/write, which Contributor does not have). Owner covers both. Verified
As Owner. Contributor plus User Access Administrator has not been run on its own.

Google Cloud

The Cloud Asset Inventory and Cloud Resource Manager APIs must be enabled in the project, as must each API whose resources are captured.

UseGrantStatus
Capture, diff roles/viewer and roles/cloudasset.viewer on the project. Verified
On 2026-10-23, a service account holding exactly these captured a sandbox project to the same digest as its owner. With roles/viewer alone the capture fails loudly: Cloud Asset Inventory answers 403.
Restore roles/editor, plus roles/iam.serviceAccountAdmin and roles/iam.roleAdmin for service accounts and custom roles. Expected
Restores have run as the project's owner.

Kubernetes

UseGrantStatus
Capture, diff list on every resource type, cluster-wide, and nothing else. Not get: on * it covers subresources too, so it reaches the kubelet through nodes/proxy and opens a shell through pods/exec. The built-in view ClusterRole leaves out Secrets: their values are never captured, but without list on them their existence is not either. Note that list on Secrets does return their values to whoever holds the role. Verified
On every test run, against a real API server with RBAC: an identity bound by exactly the role truthform permissions writes captured every type, and was refused get on Secrets, pods/exec, nodes/proxy and any write. Not yet verified on a managed cluster.
Restore cluster-admin. A restore recreates Roles and bindings, and Kubernetes lets an identity grant only what it already holds, so a narrower role fails on the first Role with a verb it lacks. Verified
With cluster-admin, on kind clusters.

GitHub

The token comes from GITHUB_TOKEN. With a fine-grained token, grant these, read-only for a capture and read and write for a restore:

  • Organization: Administration, Custom properties, Webhooks, Secrets, Variables, Self-hosted runners (runner groups), Actions policies.
  • Repository (all repositories in scope): Administration, Actions, Environments, Secrets, Variables, Webhooks, Pages, Metadata.

A classic token needs repo and admin:org. read:org is not enough: GitHub answers the organisation's Actions settings, secrets, variables and runner groups with “You must be an org admin”.

Partly verified A capture with a classic token lacking admin:org read every repository collection and was refused exactly ten organisation collections, each naming the fine-grained permission above. It reported them as failed, not as empty. The full fine-grained set has not been run on its own.

Cloudflare

Sign in through the browser with truthform login cloudflare. The full edition asks for zone.read, dns.read and dns.write; the capture-only edition asks for no write. Or set a token in CLOUDFLARE_API_TOKEN, which is used first: Zone: Read and DNS: Read for a capture, Zone: Edit and DNS: Edit for a restore, scoped to the account.

Verified for a capture: a real account was captured through the browser sign-in, with its read access. Expected for a restore, which has not yet been run against a real Cloudflare account.

What TruthForm does with the access it is given

  • Capture and diff never write. Every client that talks to a platform sits behind the read-only guard, which refuses any request that is not a read before it leaves the machine. It is an allow-list, so a request it does not recognise is refused, never let through. The capture-only edition also refuses to restore.
  • Secret values are named, not written. Values the platforms mask or never return (passwords, keys, a webhook's secret) are named in the snapshot and supplied at restore with --values, which is read and sent to the platform, never written. Kubernetes Secrets, and credentials left as plain values in an env list or a ConfigMap, are withheld the same way. A credential hidden in a command argument or in a config file is not recognised and is captured as configuration; see the getting started page.
  • A refused read is a failure, not an empty result. A missing permission shows in coverage.yaml and REPORT.md and makes the capture exit 3 (incomplete).
