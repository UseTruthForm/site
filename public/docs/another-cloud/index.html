To another cloud (Azure to AWS or Google Cloud)

truthform translate rewrites an Azure snapshot as a snapshot for AWS or Google Cloud. It reads one snapshot and a map, writes a snapshot per target, and makes no request, so the capture-only edition has it too. plan, restore and diff take what it writes as they take any snapshot.

Where it stands. Translations are restored into simulated AWS and Google Cloud APIs, and the dry run has been run read-only against a test AWS account and a test Google Cloud project. No translation has yet been restored into a real AWS or Google Cloud account. Azure is the only source.

truthform translate --from snap/azure --map map.yaml --out moved/
truthform restore --platform aws --region eu-west-1 --from moved/aws --dry-run
truthform restore --platform aws --region eu-west-1 --from moved/aws

Every object has an outcome

The translation writes translation.yaml beside the snapshots it makes, with an entry for every Azure object:

StateMeaning
mappedWritten for the target, with nothing lost.
mapped with lossesWritten, and each setting that could not be carried is named, including anything that leaves the target less protected than the source.
refusedNot written, with the reason: a choice the map did not make, something with no faithful equivalent, or identity that is the customer's directory.
not looked atA type the translation does not cover yet. It is listed, never silently dropped.

The run exits 3 when anything is refused, not looked at, less protected than the source, or has a setting no rule reads. A partial translation never looks like a finished one.

The map

The mapping itself is fixed. The map is the only input per environment: which destination each service class goes to, the region, and what Azure cannot say, such as an instance type for a node pool or a database. Nothing the map leaves out gets a default: a choice it has to make and does not is refused, naming the key. An abridged map for AWS:

to: aws                     # or gcp
region: eu-west-1
destinations:
  messaging: sqs-sns        # sqs-sns (aws), pubsub (gcp), or rabbitmq (in the cluster)
  network: vpc
  secrets: secret-manager   # Secrets Manager (aws) or Secret Manager (gcp)
  registry: ecr             # ecr (aws) or artifact-registry (gcp)
  storage: buckets          # a bucket per blob container
  dns: route53              # route53 (aws) or cloud-dns (gcp)
  databases: rds            # rds (aws) or cloud-sql (gcp)
  clusters: eks             # eks (aws) or gke (gcp)
  identity: workload        # the clusters' workload identities and their data roles
network:
  zone: eu-west-1a          # an Azure subnet spans the region's zones; an AWS one is in one
  defaultOutbound: nat      # Azure's default outbound access as a NAT (billed); without it, no egress
clusters:
  rg/shop:
    roleArn: arn:aws:iam::111111111111:role/eks-shop
    nodeRoleArn: arn:aws:iam::111111111111:role/eks-nodes
    pools:
      system:
        instanceType: m7i.xlarge    # VM sizes are not translated
databases:
  data/shop-pg:
    instanceClass: db.m6g.large     # no SKU translation, and no default

Each object is built through AWS's CloudFormation registry or checked against Google's Discovery documents, so what is written is what the target's own definition accepts. Blobs, rows, secret values and images are never copied: buckets, databases, secrets and registries are written empty, and the report says so. Virtual machines are not translated.

Never more open than the source

Azure evaluates a network security group by priority, the first match deciding. An AWS security group only allows, and adds up with the others on an interface. So each allow is written with every deny before it taken out, as address ranges, ports and protocols. An NSG on a subnet and another on an interface in it are written once, as what both allow, never side by side. What cannot be written exactly, such as a rule that names a service tag, is narrowed or dropped, and named. A translation may let through less than the source, never more.

Evidence for an audit

Each NSG's entry in translation.yaml has an evidence row for every rule, Azure's six defaults included, in every place the NSG is written:

- source: Microsoft.Network/networkSecurityGroups sec/app-nsg
  state: mapped with losses
  evidence:
  - where: AWS::EC2::SecurityGroup app-nsg
    rule: deny-ssh
    priority: 200
    direction: inbound
    access: deny
    status: exact
    enforcedBy:
    - 'AWS::EC2::SecurityGroup app-nsg: security groups only allow, and no rule of it allows what this denies'
StatusMeaning
exactThe target lets through, and keeps out, what the rule did. enforcedBy names the target rules.
stricterThe target lets through less; why says what, and for which reason.
not carriedAn allow that is not written, so nothing it allowed gets through. Never a deny: a deny that cannot be written exactly is widened, and one that cannot be read refuses the NSG.
does not applyThe rule names addresses or a group not in this place, so Azure did not apply it there either.

The rows come in a fixed order, so two runs compare line by line. The claim behind them, that the target never lets through what Azure denied, is tested by putting the same packets to Azure's rules and to each target's rules as that cloud evaluates them.

Workload identity

With identity: workload, an app that reached a queue, a blob, a secret or an image through its pod's managed identity reaches the translated one, and nothing else. A grant is written only when it is no more than the source's; in doubt, the role assignment is refused and says why.

  • What is translated: a user-assigned identity federated to a translated cluster's service account, as an IAM role trusted by EKS Pod Identity for that service account only, or a Google service account bound to it. Its data roles (Service Bus sender and receiver, Storage Blob reader and contributor, Key Vault secrets user, AcrPull and similar) come from a fixed table of each role's published actions.
  • Narrowed: a grant on a namespace, an account, a vault, a resource group or the subscription becomes a grant on each translated object in it, by name, and the narrowing is named.
  • Refused: Owner, Contributor and other control-plane roles, custom roles, conditions, and any grant to a person, a group or a pipeline. People and pipelines are the customer's directory, not the translation's.

Your Git repository

Translate does not rewrite a Kubernetes manifest. Restoring the cluster's snapshot on the target brings GitOps back and it rebuilds the rest, but the manifests in Git still name Azure things. Given the cluster's snapshot, a checkout of the repository, or both, translate lists every place that does, by file and line, with what it becomes:

truthform translate --from snap/azure --map map.yaml --out moved/ \
  --kube snap/kubernetes --gitops ~/src/fleet

An image in an Azure registry gets its ECR or Artifact Registry address; a KEDA trigger on a Service Bus queue gets the SQS or Pub/Sub trigger that replaces it. Something that names an Azure thing the translation does not hold is listed apart, because applied as it is it would still point at Azure.

The dry run

Before a translation is restored, restore --dry-run on AWS or Google Cloud reads the target and lists each write the restore would make, with what is already there and what differs, and makes none. It also reads for what would refuse a write: a bucket name someone else holds, a role or service account a resource names that does not exist, and on Google Cloud an API not enabled, with the command to enable it. What it could not check is printed as NOT CHECKED, never passed over. It cannot say whether the cloud would accept each request: quotas and refused values show only in a real restore.

Skills for what is left to people

A translation names what it does not do. For the larger parts of that, TruthForm carries skills: instructions an AI agent loads to help a person finish the work. Each reads its work list from translation.yaml, has the agent propose and check, and leaves every write or grant to the person.

SkillFor
translate-move-dataBlobs, images, secret values, databases and volumes, checked by counts, bytes and digests on both sides.
translate-grant-accessThe refused role assignments: people, groups, pipelines, control-plane and custom roles.
translate-rebuild-machinesVMs, scale sets and firewall appliances, and the security groups or tags each must carry.
translate-sql-tlsA SQL Server minimum TLS version the target cannot match.
translate-flow-logsParsers and detections written for Azure's flow log records.
translate-estimate-costWhat the translation would cost on the target beside the source's bill, every row with a source for its quantity and its price.
 
truthform skills                       # list them
truthform skills translate-move-data   # print one
truthform skills --out .claude/skills  # write the folders where an agent loads them

Over MCP the same text comes from list_skills and skill. A skill cannot make a result true: each ends with what its checks do not show, such as whether a secret's value is the right one, for the person to own.

Known limits

  • No translation has been restored into a real AWS or Google Cloud account yet; restores are proven against simulated APIs.
  • Azure is the only source. Types outside the list above, and settings such as a storage account's lifecycle rules and replication, are reported as not looked at.
  • Data is never copied, and virtual machines, a cluster's own identity, add-ons and monitoring are not translated.
  • A Service Bus SQL filter matched property names whatever their case; no target does, so the report lists each name as the filter wrote it, and senders must set it so.
  • Where the target cannot set a database's oldest TLS version, the loss fails the run until the map accepts it, after the target's floor has been checked.
