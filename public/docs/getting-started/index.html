Getting started

Install the binary, point it at a system with read-only credentials, and capture a snapshot. Then diff it against what is running, or restore it somewhere else.

Install

Truthform is one binary with nothing else to install. It comes as an archive per platform: Linux, macOS and Windows, each for amd64 and arm64, in two editions. That is 12 archives (zip for Windows, tar.gz for the rest) and a SHA256SUMS file to check them against.

Truthform is not publicly released yet, so there is no download page: archives are sent to early users directly.

For Linux on amd64, check the archive, unpack it and confirm the build. The file names carry the version, written here as VERSION.

sha256sum -c SHA256SUMS --ignore-missing
tar -xzf truthform_VERSION_linux_amd64.tar.gz
./truthform_VERSION_linux_amd64/truthform version

Then put truthform (truthform.exe on Windows) on your PATH. truthform version names the version, commit and edition, so any binary can be traced to its build.

EditionCanUse it for
fullcapture, diff, restoreEnvironments you own and intend to change.
capture-only
(file names end _capture-only)		capture, diffAssessments and audits. It refuses to restore, and every request it makes to a platform goes through the read-only guard, so it cannot change anything it reaches.

Credentials

Truthform uses each platform's standard credentials, from the environment it runs in. Give a capture a read-only role and a restore a write role, separately: the permissions page lists the exact grants.

PlatformCredentialsTarget flags
KubernetesYour kubeconfig (--kubeconfig to use another file)--context
AWSThe AWS SDK's default chain: shared config and credential files, SSO, environment variables--region, --profile
AzureThe Azure SDK's default chain, so az login works--subscription
Google CloudApplication Default Credentials (gcloud auth application-default login)--project
GitHubA token in GITHUB_TOKEN--account (the organisation)
CloudflareA browser sign-in (truthform login cloudflare), or a token in CLOUDFLARE_API_TOKEN, which is used first when set--account (the account ID)

Tokens are read from the environment and never written. A Cloudflare browser sign-in is kept in the operating system's keychain, and truthform logout cloudflare removes it. Besides each platform's API, Truthform downloads the schemas the platforms publish: AWS's CloudFormation registry schemas, Azure's type definitions, Google's Discovery documents, and GitHub's and Cloudflare's OpenAPI descriptions. There is no Truthform service for it to call.

Signing in to Cloudflare

A person at a keyboard needs no Cloudflare token made by hand. truthform login cloudflare opens Cloudflare's sign-in in a browser, you approve Truthform there, and capture, diff and restore then use that sign-in. truthform check does not: it reads only CLOUDFLARE_API_TOKEN.

truthform login cloudflare
truthform login cloudflare --no-browser
truthform logout cloudflare
  • What it asks for: zone read and DNS read, plus DNS write in the full edition only. A sign-in made with the capture-only edition grants no write at all, so a restore needs one made with the full edition.
  • Where it is kept: in the operating system's keychain (Secret Service on Linux, macOS Keychain, Windows Credential Manager), and refreshed as it expires. On a machine with no keychain, such as a bare server, login says so and stores nothing; set the token instead. No file is written in its place. It finds this out only after you have approved the sign-in, so the grant then exists at Cloudflare with nothing kept here: revoke it in the dashboard.
  • A token comes first: CLOUDFLARE_API_TOKEN, when set, is used in place of the sign-in, for CI and machines with no browser. Each run says which of the two it used.
  • --no-browser prints the address to open and waits, for when Truthform cannot open a browser itself. The browser still has to be on the same machine: Cloudflare sends the answer back to a port on localhost. A sign-in left unfinished for five minutes ends.
  • truthform logout cloudflare forgets the sign-in on this machine. To end the grant itself, revoke Truthform in the Cloudflare dashboard.
  • Your own OAuth client: set TRUTHFORM_CLOUDFLARE_CLIENT_ID to sign in as another client registered with Cloudflare, such as your organisation's own, in place of Truthform's. Keep it set on every later run, since the sign-in is refreshed under it. The client has to be registered with the redirect addresses http://localhost:8976/oauth/callback and http://localhost:8977/oauth/callback.

Grant access, then check it

truthform permissions writes the grant a capture needs, as a template for the platform's own tool, with every command to deploy, verify and remove it. It grants nothing itself. truthform check then says who Truthform runs as, what that identity holds beyond what it needs, and what it can read, type by type, from a trial capture written nowhere. On Azure, with $SUB your subscription ID and $ID the object ID of the service principal Truthform will run as:

truthform permissions --platform azure --subscription "$SUB" \
    --principal-id "$ID" --principal-type ServicePrincipal
truthform check --platform azure --subscription "$SUB"

Run check signed in as that principal. A value permissions needs and was not given is an error that says how to find it; it never prints a command with a placeholder in it.

A type refused for want of permission is reported as denied, never as empty. A type the platform kept throttling until the retries ran out is reported as throttled: that is not a permission, and the same check run later, or with a lower --parallel, reads it. The permissions page explains each grant.

Capture

Capture always only reads. In these commands, prod stands for your own kubeconfig context and AWS profile, my-org for your GitHub organisation, and $CF_ACCOUNT for your Cloudflare account ID. The Azure and Google Cloud lines take the subscription and project your CLI is currently set to.

truthform capture --context prod --out snap/k8s
truthform capture --platform aws --region us-east-2 --profile prod --out snap/aws
truthform capture --platform azure --subscription "$(az account show --query id -o tsv)" --out snap/azure
truthform capture --platform gcp --project "$(gcloud config get-value project)" --out snap/gcp
truthform capture --platform github --account my-org --out snap/github
truthform capture --platform cloudflare --account "$CF_ACCOUNT" --out snap/cloudflare

Each snapshot directory holds:

  • REPORT.md: for people. It leads with anything incomplete, then says what was captured, what was skipped and why, and what a restore will need.
  • objects/: one YAML file per resource.
  • schemas/: the fields every captured type published at capture time, so truthform schema-diff old/ new/ can show what an API added or removed.
  • coverage.yaml: everything that was read, skipped or not captured, each with a reason.
  • snapshot.yaml: with a digest. Two captures of an unchanged system have the same one, and the snapshot stores no capture time or machine details.

What a snapshot never holds, by design:

  • Data: bucket objects, blobs, database rows, queue messages, volume contents.
  • Secret values: passwords, keys, a webhook's secret, and a webhook URL that is itself a credential (Slack, Discord, Teams, a ?token= or user:pass@ URL). They are named in the snapshot and supplied at restore.
  • Credentials left as plain configuration in Kubernetes: a value named like one (*_PASSWORD, *_TOKEN, *_SECRET, API_KEY, *_KEY, *_DSN and similar) in any env list (pod templates, Argo and Tekton steps, a HelmRelease's values) or as a ConfigMap key, and any such value that is a URL with a password in it. It is named in the snapshot (truthform.org/withheld-env), REPORT.md lists it as a finding to move into a Secret, and a restore reads it from the source with --secrets-from-context. Not recognised: a credential in a command argument, inside a config file a ConfigMap holds, or in Helm values outside an env list. Because both sides are withheld, a diff does not show a rotated credential. A snapshot taken before Truthform withheld these values still holds them, including in git history.
  • What the platform made itself: default VPCs and subnets, built-in roles, provider-managed policies, a Kubernetes distribution's add-ons, such as what AKS installs and upgrades itself and what an addon manager keeps as shipped (--include-system captures these). Capture a fresh account or cluster once and pass it as --baseline to skip anything identical to it.
  • What something else creates and replaces: on AWS, what a CloudFormation stack or an AWS service owns; on Azure, a resource another resource manages, and what an AKS cluster is recognised to have made in its node group, such as its node scale set and load balancers. Restoring them would fight what makes them, and each scale-out would read as drift. REPORT.md lists each one under "Skipped on purpose" with its reason, and --capture-managed captures them anyway. Something else in a node group, such as a storage account a person put there, is captured, and a restore applies it after the cluster has made the group again. So is a role assignment on the group itself. REPORT.md lists these too, in case one was the cluster's after all, and lists under "Check before relying on a restore" what may not come back: a data disk attached to a VM, a lock on something left out, and everything in a group some other service manages.
  • What is only taken to be AKS's: on Kubernetes, a cluster-scoped object that Eno, the tool AKS manages some of its own objects with, applied or labelled, and that also has an AKS name, group or key. A person's object could carry the same marks, so REPORT.md names each one under "Taken as the platform's", and --capture-platform keeps them.
  • What a Kubernetes controller makes: pods, ReplicaSets and Jobs, which the Deployment, DaemonSet or CronJob that owns them makes again. coverage.yaml records them once per owner rather than once per instance, so new pod names after a rebuilt node, or a new Job run, leave the snapshot unchanged.

Limit a capture to some types with --types, for example --types 'AWS::EC2::*,AWS::IAM::Role'. A full AWS region, about 1,500 types, takes around five minutes. If a read is refused, the capture still writes the snapshot, names the gap and exits 3, so a missing permission never looks like an empty account.

Every platform limits how fast it is read, and Truthform waits as each one documents: Azure's Retry-After, Google Cloud's backoff, and GitHub's and Cloudflare's rate-limit headers, sending nothing more once a limit is spent, so Cloudflare never locks the account out. A wait past 15 minutes (GitHub's hourly limit) is not sat out. A read that stays throttled is reported as throttled, never as empty or denied; capture again later. On AWS, Azure and Google Cloud, a lower --parallel (8 calls in flight by default) eases a throttled account.

Diff

truthform diff --platform aws --region us-east-2 --profile prod --from snap/aws

Diff reads the live system under the same rules as the capture and lists what was added, removed or changed, field by field. It exits 2 when there are differences, so it can gate a pipeline or raise an alert. On Azure it also lists as not working, and exits 2 for, a resource that failed to provision or a peering that is not connected, whose configuration can match perfectly well. If you captured with --types, --baseline or --capture-managed, pass the same to diff; it refuses a snapshot captured under different rules rather than report a misleading difference. Two snapshots can be compared offline with truthform compare.

After a restore, give the diff what the restore was given, so it compares the target with what was sent and not with the source:

  • --values (Azure): the same file the restore took. What the file sets is compared as it was sent, so a VM size or a setting you changed on purpose is not shown as drift. Secret values are not compared. A key that matches nothing in the snapshot is refused. A diff of any other platform refuses --values.
  • --rename and --new-role-assignment-ids (Azure): the same as the restore, described below.
  • --subdomain, --address and --target (Cloudflare): the same as a subdomain restore.

Restore

Restore needs the full edition and write access. It never deletes a resource. Here dr is your own AWS profile for the account you are restoring into, and staging your own kubeconfig context.

truthform restore --platform aws --region us-east-2 --profile dr --from snap/aws --values secrets.yaml
truthform restore --context staging --from snap/k8s --secrets-from-context prod
  • By default, a restore only creates what is missing. A resource already there and identical counts as applied; one that is there but different is reported with the fields that differ, and left alone.
  • --update also brings differing resources in line with the snapshot. It never replaces one: a change the platform can only make by deleting and re-creating (an AWS create-only property) is refused and named. Kubernetes restores always apply, with server-side apply.
  • References are remapped. The snapshot holds references, not the source's IDs: a subnet's VPC, a role's ARN or a principal ID resolves to what the target created.
  • In stages, on Azure: --types 'Microsoft.Network/*' restores those types and their children. Resource groups always come, a pattern that matches nothing is refused, and what a selected resource needs must already be there. A lock waits for a run that covers everything, since it would refuse what comes after it.
  • Secrets. On AWS, Azure, GitHub and Cloudflare, --values takes a YAML file of the values the platform never returns, keyed by resource. It is read and sent to the platform, never written, and the restore names every secret it was not given. The same file can set any other property, such as a VM size the target cannot have; a list it sets is replaced whole. On Azure a key that matches nothing in the snapshot is refused, and diff takes the same file. On Kubernetes, --secrets-from-context reads the values live from a source cluster and sends them straight to the target; a secret with no values is refused.
  • Into another AWS region: restore from the snapshot with a different --region. Zones are paired by zone ID and the pairing is printed; --zone-map use2-az1=use1-az4 overrides a pair.
  • Into another Azure subscription while the source exists: storage accounts, key vaults, container registries, SQL servers and Service Bus namespaces have names unique across Azure, so the restore would fail on them. --rename names.yaml gives them new names, one Type/name: newname per line, such as Microsoft.Storage/storageAccounts/shopassets01: shopassets02. Their children, the role assignments, locks and diagnostic settings on them, and every reference to them follow. Text that only mentions an old name, such as a host name in an app setting, is left as it is and listed on standard error so you can check it. Write --values with the snapshot's names, and give diff the same file. An entry that names nothing in the snapshot, a resource group, or two resources given one name is refused, and other platforms refuse --rename.
  • In parallel: on AWS, Azure and Google Cloud, resources that do not depend on each other are created together, 8 at a time by default (--parallel).
  • See it first (GitHub, Cloudflare): --dry-run reads the target and prints each write the restore would make, as would create or would update, and makes none. Its client refuses every write, so nothing changes even if the run goes wrong. Other platforms refuse --dry-run; there, a diff of the target from the snapshot shows what is missing.

A second environment's DNS in the same zone (Cloudflare)

--subdomain restores one zone's records a level down, beside the originals: example.com becomes test.example.com, www.example.com becomes www.test.example.com, and a CNAME to a name in the zone follows. It is for giving a test or recovery environment the same names as production without a second zone. Run it with --dry-run first:

truthform restore --platform cloudflare --account "$CF_ACCOUNT" --from snap/cloudflare \
    --subdomain test.example.com --address 192.0.2.1=198.51.100.7 \
    --target app.example.net=app-test.example.net --dry-run
  • Say where each record should point. A copy that still pointed at the source would send test traffic to production, so the restore stops if one would. --address <source-ip>=<target-ip> maps an A or AAAA record, and --target <source-host>=<target-host> maps a CNAME to a host outside the zone, such as an app service or a load balancer. Give the same address or host on both sides to keep it on purpose. Several pairs are separated by commas.
  • Only names under the subdomain are written. The zone is used as it is and never created or changed, and other zones in the snapshot are left out.
  • Each record it writes carries the comment truthform: test.example.com. Only a record with that comment is Truthform's to change, with --update. A record written before the rename, with stackdna: in its comment, counts too.
  • It reads the zone first and stops before writing anything when:
    • the zone is not in the target account;
    • a record it did not make is at a name it would write;
    • a record an earlier run made is there with other content, since DNS would then answer with both (delete it first);
    • the subdomain is delegated or is a zone of its own;
    • the snapshot has a CNAME beside other records at one name, which DNS does not allow.
  • Mail, delegations and ACME records stay out: MX, SPF, DKIM, DMARC, MTA-STS, TLS reporting, BIMI and mail clients' autodiscovery records, NS records, and _acme-challenge. So do records the source already has under the subdomain, and everything in the snapshot that is not a DNS record. The run lists each record it leaves out, with the reason.
  • It warns of a wildcard above the subdomain, such as *.example.com. Today that wildcard answers for test.example.com and every name below it. Once any of those names exists it no longer does, so a name there that the restore does not create stops resolving.
  • It also warns of a CNAME that points at a name it leaves out, which would answer with nothing, and of an SRV, HTTPS or SVCB record, whose target is copied as it is.
  • Nothing is deleted. A record an earlier run made that the snapshot no longer has is reported and left in place.
  • The subdomain name can be at most 89 characters, so the comment fits in the 100 that Cloudflare's free plan takes.

Afterwards, truthform diff with the same --subdomain, --address and --target compares the records under the subdomain with the snapshot as the restore put it.

A whole environment

List every system in one file. The context, profile and project names are your own.

name: prod
targets:
  - {name: cluster, platform: kubernetes, context: prod}
  - {name: aws,     platform: aws, region: us-east-2, profile: prod}
  - {name: gcp,     platform: gcp, project: my-project}
truthform capture --config prod.yaml --out snap/
truthform diff    --config prod.yaml --from snap/

Kubernetes contexts, AWS regions, Azure subscriptions (subscription:), Google Cloud projects, and GitHub organisations and Cloudflare accounts (account:) can be mixed. Targets are captured in parallel into snap/<target>/, and the environment gets a summary report. A target that cannot be reached is recorded as failed without stopping the others, and the exit code is the worst result. A relative path in the file (baseline, a Kubernetes target's kubeconfig) is relative to the file itself, so the command works from any folder. An AWS, Azure or Google Cloud target the platform throttles can take parallel: 4, as --parallel does for one target. The file is strict: a misspelled key or a missing field fails before anything runs. Restore stays per target, on purpose.

Exit codes

CodeMeaning
0Success: the capture is complete, the restore fully applied, or there are no differences.
1Error: bad flags, cannot connect, cannot read a snapshot.
2Differences found (diff, compare).
3Incomplete: the snapshot was written but some types could not be read, or a restore applied only some resources; check found types denied, throttled or failed.

Machine-readable output

Add --json to capture, diff, restore, compare, check or permissions, with or without --config. Standard output is then one JSON document, named by its schema field (truthform.org/output/v1), and everything meant for a person goes to standard error. The exit code does not change, and a run that fails still prints a document naming the error.

truthform diff --platform aws --region us-east-2 --profile prod --from snap/aws --json | jq '.changes'

A capture's document says whether it is complete and lists its gaps, and under throttled the gaps a later capture can close as it is; a diff's lists each change with its kind (missing, extra, changed) and fields; a restore's lists each resource with ok and detail.

As a graph (Azure)

truthform graph writes an Azure snapshot as resources and the relationships between them, as JSON, for a tool that maps an estate rather than recreating it, such as an asset inventory or a security graph. It reads only the snapshot, with no login and no request, and both editions have it. Other platforms' snapshots are refused.

truthform graph --from snap/azure --out graph.json
truthform graph --from snap/azure --subscription "$SUB" --tenant "$TENANT" --out graph.json
  • Nodes are resources: id, type, name, group, location, tags and the chosen properties, keyed by path (properties.publicNetworkAccess). A node marked external is something the snapshot refers to but does not hold, such as another subscription's network or a built-in role definition. A node with managedBy is something capture left out because that resource manages it, such as the load balancers and public IPs in an AKS cluster's node group. Only its ID, type and name are known: it was not read, so it says nothing about its address or rules, and a public IP there may only be the cluster's way out. --capture-managed reads them.
  • Edges run from the resource holding a relationship to the one it names, each with a kind: references (path says which field), child-of, extension-of (a role assignment, lock, policy assignment or diagnostic setting on what it is attached to), depends-on (a resource created by another, such as an AKS cluster's managed group) and managed-by (something capture left out, to what manages it). A reference to a part kept inside a resource, such as a subnet, goes to that resource, and subresource names the part (subnets/app).
  • --types chooses each type's properties. The built-in security, the default, keeps network exposure, identity and access, encryption, public access, private endpoints and diagnostics, and leaves out types with no security signal. none gives every resource without properties, and a file in the same format gives your own.
  • IDs keep the snapshot's subscription and tenant placeholders unless --subscription and --tenant give the real ones. Another subscription a resource refers to keeps its real ID either way. A manager is taken to be in the captured subscription, because nothing in a snapshot says which subscription that is.
  • generator names the version and commit that wrote the file.

The same snapshot gives the same graph, byte for byte, from any binary of one release. Another build can change the file even where nothing else has changed, so across builds compare nodes and edges. A graph holds what its snapshot holds, so keep it as carefully.

Known limits

  • Data is never captured, only configuration.
  • S3 bucket names are global: a bucket cannot be restored under the same name while the original exists, or in another region shortly after it was deleted.
  • A few fields are accepted on write but never read back, such as a GitHub environment's wait timer. The snapshot names them (truthform.org/unreadable) and a restore says it could not carry them.
  • A Log Analytics workspace's data sources can only be listed one kind at a time. Truthform lists every kind Azure's definition names; a data source of a kind it does not name is not found.
  • Proven against real systems so far: Kubernetes; AWS (capture of a whole region; restore of the 17 types the drill uses, an IAM role, a managed policy and a Lambda function among them; --update of resources drifted by hand; restore into another region); Azure; Google Cloud; GitHub and Cloudflare capture. GitHub and Cloudflare restore, and Google Compute, are proven against simulated APIs only.
  • On Cloudflare, a --subdomain restore has not yet written to a real zone, and the browser sign-in has not been tried on Windows or macOS.
  • On Cloudflare, a record is matched by its type, name and content together, so one whose content changed is a different record and --update does not change the old one. A --subdomain restore stops and asks for the old one to be deleted first. A restore without --subdomain creates the new record beside the old.
  • On AWS, restores into another account have not been run against real AWS yet, nor IAM beyond a role and a customer managed policy.
  • On Azure, --rename is proven by the simulated drill, which restores a renamed snapshot and gets an empty diff, and by an offline run over a real snapshot of about 1,600 objects. A real restore into a second subscription has been run; its results are not published here yet.
  • On Azure, a role assignment for a principal the snapshot does not hold (a person, a group, an application) keeps its object ID, so it fails with PrincipalNotFound in another tenant: Truthform does not map principals across tenants.
  • On Azure, within the source's tenant, role assignment names are taken while the source exists, so pass --new-role-assignment-ids to the restore and to a diff of that target. A custom role's ID is unique per tenant too. A restore will not take over one other subscriptions use: add the target to its assignableScopes and run again, and the role is then taken as it is, never changed.
  • On Azure, a VNet peering to a network in another subscription keeps that network's ID, so a restore connects to it if the identity may. Check any before restoring.
  • On Azure, the rule for what an AKS cluster made rests on one real cluster, and something a person put in a node group whose type AKS also makes, such as an NSG, is skipped as the cluster's.
  • On Azure, a snapshot does not name the subscription, apart from the title of REPORT.md and a resource whose own name holds it, such as DefaultWorkspace-<id>-EUS. A graph does not name it unless you pass --subscription.
